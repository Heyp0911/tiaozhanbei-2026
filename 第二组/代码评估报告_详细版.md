## 一、致命问题（P0 —— 答辩时可能被直接质疑）

### 问题 1：全部输入数据（除气象外）均为合成数据

**涉及文件**：多个

**问题描述**：

整个模型链路中，唯一真实的数据来源是 NASA POWER 的气象数据（GHI、DNI、DHI、T2M）。其余全部输入均为数学构造：

| 数据 | 来源 | 真实性 |
|------|------|:---:|
| 基础负荷曲线 | `generate_base_load.py` 高斯+正弦+随机噪声合成 | ❌ 完全虚构 |
| 闽清小水电出力 | `green_power_predictor.py:306-318` 用 `sin` 函数构造 | ❌ 完全虚构 |
| AI 任务负荷（刚性/弹性/温冷比例） | `params.json` 手工设定 | ❌ 无依据 |
| 光伏装机 50MW、算力节点 5MW | `params.json` 手工设定 | ❌ 假设值 |
| 储能参数 | `params.json` 文献参考值 | ⚠️ 非闽清实测 |
| 分时电价 | `params.json` 福建省发改委文件参考值 | ✅ 有依据 |

**为什么这是致命问题**：

赛题明确要求"闽清县参数替换方案"和"闽清县典型场景验证"。当前代码的"闽清验证"只是在通用合成数据上换了一天的气象输入，**负荷结构、小水电数据没有做任何闽清-specific 的替换**。这不是真正的"验证"，只是"换了天气参数重跑一遍通用模型"。

**修复方案**：

1. **短期（比赛截止前可做）**：
   - 在报告中**诚实标注**哪些数据是合成的、哪些是真实的
   - 至少查一下闽清县的公开信息：陶瓷产业用电占比、小水电总装机量、典型日负荷特征
   - 让 `minqing_load_adjust` 参数在 `milp_optimizer.py` 中**真正生效**——目前 `params.json` 中定义了 `minqing_load_adjust.ceramic_industry_ratio=0.25`，但代码中完全没用到

2. **中期（如果入围答辩）**：
   - 设法获取闽清县真实的负荷数据或产业用电比例
   - 用真实的小水电历史出力数据替换正弦波模型

**具体修改位置**：

- `milp_optimizer.py:488` — 闽清验证的 `base_load` 直接用了通用合成数据，没有用 `minqing_load_adjust` 做任何调整
- `params.json:93-99` — `minqing_load_adjust` 字段定义了但未被使用

## 二、严重问题（P1 —— 削弱论证力）

### 问题 3：改善幅度太小（~1%），论证力弱

**涉及文件**：`milp_optimizer.py`、`params.json`

**实际数据**（来自 `outputs/通用模型/metrics_summary.csv`）：

| 指标 | 场景二(电随算走) | 场景三(算随电走) | 差异 |
|------|:---:|:---:|:---:|
| 绿电消纳率 | 86.41% | 87.48% | **+1.07pp** |
| 系统成本 | 12,118 元 | 11,954 元 | **-1.4%** |
| 碳排放 | 149.2 kg | 147.3 kg | **-1.3%** |

**根本原因**：场景二（固定算力）本身已经消纳了 86.41% 的绿电。场景三只能在剩余 13.59% 的弃电中抢优化空间。1.07 / 13.59 ≈ 只能抢回 8% 的剩余弃电。

**修复方案（按推荐顺序）**：

A. **进一步放大光伏-负荷的不匹配度**（推荐）：
   - 在 `params.json` 的 `milp_scene_config.general_model` 中选择光伏峰值更高 + 负荷更低的组合
   - 当前配置：`pv_scene_index=0`（峰值最高的场景）, `load_scene_index=3`（周末轻载日）。这个组合已经是最极端的了，需要调到参数层面。
   - 可尝试增大 `P_rated_MW`（当前 50MW）到 60-80MW，或降低 `P_peak_MW`（当前 50MW）到 30-40MW

B. **继续增大弹性任务占比**：
   - `params.json:44` — `E_elastic_daily_MWh` 当前 57.6（60%），可调到 67.2（70%）
   - 同时从刚性任务中减掉对应的量

C. **拉大峰谷电价差**：
   - `params.json:64` — peak_price 当前 1.20，可调到 1.40
   - `params.json:75` — valley_price 当前 0.30，可降到 0.25
   - 增大电价差会让 MILP 有更强的动力把任务推到谷段（光伏高峰时段）

D. **在报告中诚实定位**：强调"在最保守的参数设定下，算随电走仍持续优于电随算走"，将"小幅但稳健"转化为优势。

### 问题 4：闽清波动日完全无区分度

**涉及文件**：`green_power_predictor.py:213-268`（`select_validation_dates` 函数）

**当前状态**：

波动日（2025-04-19）的三场景绿电消纳率分别为 99.92% / 100% / 100%，几乎无差异。原因是该日光伏出力偏低，总绿电几乎全部被消纳，没有弃光压力。

**修复方案（三选一）**：

**方案 A（推荐）**：换一个光伏出力更高但 GHI 变异系数更大的日期。修改 `green_power_predictor.py:256`：

```python
# 当前代码（只取变异系数最大的一天）：
volatile = df_daily.nlargest(1, "ghi_cv").iloc[0]

# 改为：在日照时长 > 8h 的日中，取变异系数最大的
volatile_candidates = df_daily[df_daily["sunlight_hours"] >= 8]
volatile = volatile_candidates.nlargest(1, "ghi_cv").iloc[0]
```

**方案 B**：如果不想改代码，在报告中将波动日定位为"压力测试底线场景"——"即便在最不利条件下（光伏出力接近负荷下限），算随电走仍不劣于电随算走，且在削峰填谷上有额外收益"。

**方案 C**：从三个验证日期中去掉波动日，只保留晴天+中等日照两个场景，波动日数据放入附录。

### 问题 5：闽清验证实际上没有替换负荷参数

**涉及文件**：`milp_optimizer.py:455-549`（`run_minqing_validation` 函数）、`params.json:93-99`

**问题描述**：

`params.json` 中定义了 `minqing_load_adjust`：

```json
"minqing_load_adjust": {
    "ceramic_industry_ratio": 0.25,
    "residential_ratio": 0.35,
    "commercial_ratio": 0.25,
    "agriculture_ratio": 0.15,
    "_note": "闽清以陶瓷工业为特色，工业占比提高"
}
```

但在 `milp_optimizer.py:488`：

```python
base_load = load_df[load_df.columns[params.get('milp_scene_config', {}).get('minqing_validation', {}).get('load_scene_index', 3)]].values
```

**直接使用了通用合成负荷，完全没有用 `minqing_load_adjust` 做任何调整。** 这意味着闽清"验证"跟通用模型用的是完全相同的负荷数据——唯一的区别是换了气象输入和加了小水电。

**修复方案**：

在 `milp_optimizer.py` 的 `run_minqing_validation` 函数中（约第 488 行后），加入负荷调整逻辑：

```python
# 读取闽清负荷调整参数
load_adj = params.get('minqing_load_adjust', {})
if load_adj:
    # 调整负荷结构：增加陶瓷工业占比
    # 例如：通用模型 居民40%+工商业45%+农业15%
    #       闽清模型 居民35%+工商业50%(陶瓷25%)+农业15%
    ceramic_ratio = load_adj.get('ceramic_industry_ratio', 0.25)
    # 按比例修正 base_load（具体实现取决于 base_load 的数据结构）
    # 至少要在日志中打印闽清负荷调整信息
    print(f"   闽清负荷调整: 陶瓷工业占比={ceramic_ratio}")
```

**最低要求**：如果无法获取闽清真实负荷数据，至少在控制台打印一条明确的日志说明"当前使用通用负荷数据"，并在报告中诚实标注。

## 三、中等问题（P2 —— 影响严谨性但不致命）

### 问题 6：场景二中"固定算力"实际不固定

**涉及文件**：`milp_optimizer.py:194-202`

**问题代码**：

```python
elif scenario == "fixed":
    # 固定场景：P_elastic和P_cold是固定值，Python验证即可
    for t in range(hours):
        total_compute = P_rigid_demand[t] + P_elastic[t] + P_cold[t] + P_node_idle
        if total_compute > P_node_rated:
            # 如果超出容量，等比例缩减
            scale = (P_node_rated - P_rigid_demand[t] - P_node_idle) / (P_elastic[t] + P_cold[t])
            P_elastic[t] *= scale
            P_cold[t] *= scale
```

当节点容量不够时，代码**静默地等比例缩减**弹性/温冷任务。这意味着"固定算力"场景在某些参数组合下并不是真正固定的。且没有任何日志输出这个行为变更。

**修复方案**：

在缩减发生时打印 warn 日志：

```python
if total_compute > P_node_rated:
    print(f"   [WARN] 场景二 t={t}: 算力需求({total_compute:.2f}MW)超出节点容量({P_node_rated}MW)，等比例缩减")
    scale = (P_node_rated - P_rigid_demand[t] - P_node_idle) / (P_elastic[t] + P_cold[t])
    P_elastic[t] *= scale
    P_cold[t] *= scale
```

或者更好的做法：在 params.json 中调整参数使得场景二不会触发容量超限。

### 问题 7：MILP 求解器中存在无解释的 magic number

**涉及文件**：`milp_optimizer.py:135-136`

**问题代码**：

```python
effective_grid_max = max(P_grid_max, max_possible_load - np.max(pv_avail) + 2)
```

`+ 2` 为什么是 2？这看起来像是为了让求解器有足够裕量而拍脑袋加的。

**修复方案**：

```python
# 电网上限取 max(配置值, 最坏情况供需缺口)，外加 10% 余量确保可行域非空
worst_case_deficit = max(0, max_possible_load - np.max(pv_avail))
margin = 0.10 * max_possible_load  # 10% 余量
effective_grid_max = max(P_grid_max, worst_case_deficit + margin)
```

### 问题 10：缺少中文显示的回退方案

**涉及文件**：`utils/plot_utils.py:15-16`

```python
plt.rcParams["font.family"] = "Times New Roman"
```

中文依赖 `SimHei` 字体。如果系统没有 SimHei，所有中文标签变方框。

**修复方案**：在文件开头加入字体检测：

```python
import matplotlib.font_manager as fm
available_fonts = [f.name for f in fm.fontManager.ttflist]
if 'SimHei' in available_fonts:
    CHINESE_FONT = 'SimHei'
elif 'Microsoft YaHei' in available_fonts:
    CHINESE_FONT = 'Microsoft YaHei'
else:
    CHINESE_FONT = 'sans-serif'
    print("[WARN] 未找到中文字体(SimHei/Microsoft YaHei)，中文标签可能显示为方框")
```

然后将所有 `family="SimHei"` 替换为 `family=CHINESE_FONT`。

### 问题 12：`generate_base_load.py` 中的硬编码比例

**涉及文件**：`generate_base_load.py:35`

```python
daily_profile = 0.4 * res_base + 0.45 * ind_base + 0.15 * agr_base
```

居民 40%、工业 45%、农业 15% 的比例硬编码在代码中。闽清的实际情况（陶瓷工业大县）与此不同。

```python
load_config = _params.get('base_load', {})

ind_r = load_config.get('industrial_ratio', 0.45)
agr_r = load_config.get('agriculture_ratio', 0.15)
daily_profile = res_r * res_base + ind_r * ind_base + agr_r * agr_base
```

同时在 `params.json` 的 `base_load` 段中加入这三个比例参数。

## 七、做得好的地方（保持不变）

1. **四模块架构设计**：绿电预测 → MILP优化 → TOPSIS评价 → AI Demo，模块间通过 CSV/JSON 解耦，每个能独立运行和调试。整体设计思路清晰。

2. **两层数据策略**：层一（K-Means 聚类抽象 → 通用县域模型）+ 层二（原始真实日 → 闽清验证），分别服务于报告第三章和第四章，逻辑自洽。

3. **params.json 参数集中管理**：几乎所有可调参数集中在一个 JSON 文件中，场景选择也实现了配置化。比赛中非常实用——参数争议时改一行重跑即可。

4. **手写 K-Means**：避免 sklearn 版本依赖。评委机器上不会出现兼容性问题。
